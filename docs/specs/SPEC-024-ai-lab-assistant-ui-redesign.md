# SPEC-024: AI Lab Assistant UI redesign (P1.4)

Status: implemented and verified with Node tests on a fake DOM (99 tests) and 136 checks in headless Chrome on the real page with stubbed API routes (46 wide light, 46 wide dark, 34 with a remembered width, 10 narrow). **No backend change, no real Claude call, no container started.** The checks that need the real stack are listed under "To validate manually" and in `docs/ai-builder.md` (steps 31-37).

## Original request (verbatim)

> Implement P1.4 — Modern AI Lab Assistant UI Redesign.
> The current AI Builder modal is outdated, visually cluttered and impractical. We want to redesign it as a modern, integrated AI coding assistant, similar in usability to contemporary IDE assistants. This is primarily a frontend/UI/UX task.
> IMPORTANT: Preserve all existing backend functionality, APIs, security boundaries, conversation persistence, usage tracking, validation, Undo, Reset and Publish. Do not redesign the backend.
> 1. Replace the modal with a resizable right-side panel: integrate the AI Lab Assistant directly into the Playground layout; dock the assistant on the right; make the panel resizable horizontally using a draggable divider; persist the preferred width in localStorage; provide a clear open/close control; keep the Playground and its terminals usable while the panel is open; resize the main workspace instead of covering it; on narrow screens, use a full-screen responsive panel; do not break terminal resizing or existing Playground navigation.
> 2. Modern conversation experience: a polished, contemporary chat interface: clean message layout with clear user/assistant distinction; proper Markdown rendering; syntax-highlighted code blocks; copy buttons for code snippets; comfortable typography and spacing; sticky message composer at the bottom; auto-growing textarea; Enter to send, Shift+Enter for newline; smart auto-scroll; conversation history selector; new conversation action; display the associated Lab clearly; show model, tokens and estimated cost unobtrusively. Avoid large forms and oversized banners.
> 3. Loading and progress indicators: animated, accessible loading indicators showing meaningful states such as Thinking, Analyzing Lab, Editing files, Validating, Ready, Error. Use actual backend state when available. Do not invent progress percentages or claim a specific operation is running without supporting state. The user must always understand whether Claude is working or waiting for input.
> 4. Changes and publication: integrate the existing editing workflow into the new interface: compact summary of pending changes; collapsible list of changed files; readable diff viewer with syntax highlighting; clear validation status; Undo and Reset actions; explicit approval before Publish; Publish disabled when validation fails; confirmation and feedback for destructive actions. Keep the conversation visible while reviewing changes.
> 5. Generation workflow: preserve the existing AI Builder generation workflow. Integrate it into the new panel without making it dominate the interface. The conversational assistant should be the primary experience. Users must still be able to generate, validate, review and publish new Labs.
> 6. Visual design: a modern, restrained developer-tool aesthetic: consistent spacing and typography; clear visual hierarchy; subtle borders and shadows; smooth, restrained transitions; modern buttons, icons and input controls; light and dark theme support; accessible contrast and keyboard navigation; responsive layout. Reuse existing Playground design tokens and frontend architecture where possible. Avoid introducing a large UI framework.
> 7. Technical requirements: inspect the current Playground layout and AI Builder frontend before making changes; identify existing terminal resizing and layout mechanisms; avoid duplicating event handlers or introducing competing resize logic; keep frontend changes modular; preserve existing API contracts; avoid unrelated refactoring.
> 8. Validation: test panel open/close; horizontal resizing and width persistence; Playground terminal behavior while resizing; conversation creation and reopening; message sending and loading indicators; Markdown and code rendering; changes review, Undo, Reset and Publish; generation workflow; light and dark themes; desktop and narrow viewport layouts; keyboard accessibility. Run existing tests and add focused UI tests. Do not make real Claude calls automatically.
> 9. Implementation process: first inspect the existing UI architecture. Propose the minimal integration approach, including how the Playground layout will accommodate the panel. Then implement the redesign. Use targeted edits and preserve existing functionality. Report: files changed, UI architecture, tests executed, remaining limitations, manual browser validation steps.

## Existing layout (inspected first)

`<main>` is a flex row: `aside#sidebar` (fixed basis) and `section#terminal` (`flex: 1; min-width: 0`). The terminals are iframes (one ttyd each) laid out by CSS only: the sidebar toggle changes a class, the split separators change `--cx`/`--cy` and add a `dragging` class that stops iframes from taking the pointer. There is no JavaScript resize code for the terminals: an iframe whose size changes gets a new window size and ttyd refits xterm.js by itself. `style.css` also restyles every `aside` as a short top strip below 700 px.

## Implemented

- **Docked panel.** `<aside id="aib">` is a third column of `<main>` (`flex: 0 0 var(--aib-w)`), with a separator `#aib-resizer` before it. Opening it shrinks the terminal column; the only thing JavaScript changes is the CSS variable `--aib-w`, the same mechanism the existing separators use. No `ResizeObserver`, no handler on the terminals: one window `resize` listener only re-clamps the panel's own width. While dragging, `main.aib-dragging` makes `#panes iframe` ignore the pointer. Below 800 px the panel is `position: fixed; inset: 0` (the workspace is not resized and the divider is hidden).
- **Width.** 320-720 px, always leaving 280 px to the terminals, default 440 px, persisted in `localStorage` (`aibPanelWidth`; a damaged value is ignored). Pointer drag, keyboard (←/→, Shift, Home/End) and double-click reset; the separator has `role`, `aria-orientation`, `aria-valuenow/min/max`.
- **`web/static/ai-markdown.js` (new).** A small Markdown parser and renderer (headings, paragraphs, bold, italic, strike, inline code, links limited to http(s)/mailto, nested lists, quotes, rules, GFM tables, fenced code) and a line highlighter (bash, YAML, JSON, SQL, diff). It builds DOM nodes with `textContent` only; HTML in a reply is displayed as text. Code blocks have a language label and a Copy button (Clipboard API with a `execCommand` fallback).
- **Conversation view.** Compact header (title, **Lab** chip, model, message count, context, estimated cost with a tooltip), user messages as plain bubbles, assistant replies as Markdown, a sticky auto-growing composer (Enter sends, Shift+Enter newline, never while an IME composes), smart scrolling with a **↓ New messages** button, the list rebuilt only when it changed (a selection survives polling).
- **Status line.** `AIBCore.describeActivity` maps real information to *Ready*, *Claude is thinking · mm:ss…* (from the conversation's `pending.started`), *…editing is enabled for this message* (from `pending.edit`), *Sending…*, *Validating the changes…*, *Undoing/Resetting/Starting over…*, *Publishing to usecases/<lab>…*, the last failed reply, *not available*. No percentages and no guessed sub-steps; "Analyzing Lab" and "Editing files" are deliberately not shown as live operations because the backend does not report them.
- **Changes.** Compact bar with Review/Hide changes, Undo, Reset (two clicks), "Start over" on conflict (two clicks); the review (validation chip, collapsible file list, diff viewer with colored lines and highlighted content, approval, Publish) opens above the composer so the conversation stays visible; a result line gives feedback for Undo, Reset, Start over and Publish.
- **Generation** is the second tab ("Generate a new Lab"), logic unchanged.
- Files: `web/static/index.html` (rewritten panel markup; `<main id="app-main">`), `ai-builder.css` (rewritten for the panel), `ai-builder.js` (panel controller, Markdown rendering, composer, scroll, activity, changes UI; the API calls and generation logic are untouched), `ai-markdown.js` (new), `style.css` and `app.js` untouched. Tests: `tests/ai_builder_ui_test.js` (modal-specific tests replaced, 24 new), `tests/ui-browser.sh` and `tests/ui_browser_page.py` (new), `tests/ui.sh`, `tests/static.sh`.

## Found by the real-browser checks

- `style.css` applies `max-height: 40vh` (and `0` when the sidebar is collapsed) to every `aside` below 700 px; the panel inherited it and was cut to 40% of the screen. Fixed in the panel's own CSS (`max-height: none`); the browser check now collapses the sidebar in the narrow layout.
- A table delimiter row such as `|:-:|--:|` was not recognized (cells need one hyphen, not two) and `window.__xss` was rendered with bold text (double underscores inside a word). Both fixed in the renderer with unit tests.

## Known limitations

- The browser checks use stubs and a stand-in terminal iframe; real ttyd refit, real conversations and real Claude replies are in the manual steps. The resize *event* of the terminal's window is dispatched by the browser and is not asserted (its delivery under headless virtual time is not deterministic); the terminal's viewport size, which is what xterm.js refits to, is.
- The Markdown renderer is deliberately small: no footnotes, no HTML, no images, no reference links, no task lists, and emphasis rules are simplified (an unusual nesting may render differently from CommonMark). Highlighting works line by line (a multi-line string is not tracked) and covers five languages; other languages show as plain code.
- Syntax highlighting of diffs uses the file's extension, so a hunk that starts in the middle of a construct can be colored imperfectly.
- Progress is only what the backend reports: during a message there is no sub-step (reading, editing, validating) to show.
- Not verified in a real browser by me: Safari/Firefox, touch dragging of the divider, screen reader output, high-contrast mode.
- The previous modal and its `Esc` behavior are gone; the panel is not modal and does not trap the focus (by design, so the terminals stay usable).
