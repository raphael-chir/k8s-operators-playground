# SPEC-026: Safe file deletion and Lab deletion (P4.3.2)

Status: implemented and verified with Python unit/API tests, Node UI tests and the opt-in real Claude Code CLI harness (`tests/ai_builder_real_cli.py`, disposable sandboxes only). Not verified: the container deployment itself (compose, Docker discovery), a browser session, a cluster that is started outside the web server between the last check and the move (see Known limitations).

## Original request (verbatim)

> P4.3.2 — Safe File Deletion and Lab Deletion
>
> Implement two distinct deletion capabilities: A. Delete individual files within a Lab. B. Delete an entire published Lab. These operations must use different authorization and publication workflows. Preserve all existing functionality.
>
> PART A — FILE DELETION INSIDE A LAB. Users must be able to ask the AI Assistant to delete scenarios, manifests, obsolete configuration files, remove multiple files, replace or reorganize Lab content. These are normal Lab editing operations. They must use the existing one-shot editing approval mechanism. No dedicated Lab deletion confirmation is required.
> Claude currently has Write/Edit but cannot delete files. Implement a narrowly scoped deletion capability. Preferred approach: a dedicated workspace file deletion tool exposed to Claude through the existing Claude Code tool integration mechanism. Before implementing, inspect the actual CLI/tool integration architecture and determine the smallest compatible solution. Requirements: no Bash access; no general filesystem deletion tool; only operate on the current conversation's approved workspace; only operate on explicitly approved Labs; enforce the existing one-shot approval lifecycle; reject absolute paths, path traversal, symlinks and symlinked parent directories, paths outside the approved workspace, directories and recursive deletion, protected files; preserve undo/reset compatibility and multi-Lab isolation. The deletion capability must be unavailable during read-only turns. Do not broaden Claude's filesystem permissions.
> The root usecase.yaml is mandatory. It may be edited or replaced with valid content. It must never be deleted individually. Enforce this rule in the workspace deletion operation, in backend validation and in the publisher safety checks; do not rely only on Claude's system prompt. A complete Lab deletion is a separate operation.
> Deleted files must appear in Review Changes as deleted, not modified or emptied. Before publication validate the resulting Lab (missing required files, references, invalid scenario structure, broken references where reliably verifiable); do not weaken the validator. Publication must reflect the validated workspace tree, including removed files, not overlay workspace files on the published Lab; preserve tree-hash conflict detection, atomic publication, rollback and failure handling; never delete files outside the target Lab; reject an invalid resulting Lab and a missing root usecase.yaml.
> Individual file deletion is allowed while a Lab is running: it modifies the Lab definition, not the running infrastructure. Never automatically apply Kubernetes changes, never stop or restart clusters, warn the user when relevant that published changes may not affect the currently running environment.
>
> PART B — COMPLETE LAB DELETION. Users must be able to request "Delete the clickhouse-operator Lab." This is not a normal editing operation. Claude must never empty all Lab files as a deletion workaround. Use a dedicated directive `[[context: delete LAB_NAME]]`; it creates a pending deletion request only and never executes deletion.
> The AI Assistant must check the actual infrastructure status. If the Lab is running, explain directly in the conversation: "The Lab clickhouse-operator is currently running. You must stop its infrastructure from the Playground before deleting it. Once stopped, tell me and we can continue." No deletion confirmation while running; preserve the pending intent; let the conversation continue naturally; recheck infrastructure when the user says it has stopped; never trust the user's statement without verification; never automatically stop infrastructure. If infrastructure is starting, stopping or unknown, block deletion and explain why.
> Complete Lab deletion is permitted only when the infrastructure is positively confirmed stopped. Check before presenting confirmation and immediately before executing deletion; reuse the Playground's existing infrastructure status detection; fail closed. Investigate startup/deletion concurrency; ensure a concurrent startup cannot bypass deletion safety; prefer narrowly scoped lifecycle coordination; no unnecessary global locking.
> Display a dedicated deletion confirmation card showing the Lab name, title, file count, a warning about permanent removal from the active Playground and a warning about other conversations referencing the Lab. Require the user to type the exact Lab name; the Delete button stays disabled until it matches. The backend must independently verify confirmation. Editing approval must never authorize Lab deletion.
> Backend: `POST /conversations/<id>/delete_lab`. Before deletion verify: conversation exists and is idle; Lab exists and belongs to its context; explicit pending deletion intent exists; confirmation matches; no pending changes in the target workspace; no conflicting publication or deletion; infrastructure stopped; published tree hash matches the confirmed version. Reject unsafe operations; preserve state on failure.
> Publisher: a dedicated authenticated deletion operation that validates Lab names, rejects path traversal and symlinks, verifies the expected published tree hash, rejects missing Labs and conflicting operations, never affects another Lab. Do not use rm -rf. Move the Lab atomically to usecases/.trash/<lab>-<timestamp>/ (same filesystem rename, unique destination, no overwrite, all files preserved, recovery information, excluded from Lab discovery, added to .gitignore, no automatic purge). Document manual restoration.
> After successful deletion: clear the pending request, detach the deleted Lab from the active conversation, clear associated editing approvals, refresh the frontend Lab registry, add a conversational deletion confirmation. Do not modify other conversations; preserve other conversations' workspaces and pending changes; publishing a stale workspace must fail safely; avoid destroying the deleting conversation's workspace automatically.
>
> PART C — SECURITY AND REGRESSION: baseline all existing tests before modifying code; implement incrementally; preserve Claude CLI permission isolation, read-only published mounts, workspace isolation, one-shot approvals, publisher authentication, tree-hash conflict detection, validation, session persistence, cost accounting; never grant Bash or unrestricted filesystem access. Tests for file deletion (one, several, manifest, nested, nonexistent, usecase.yaml, outside workspace, symlink, no approval, expired approval, another Lab's file, review shows deleted, undo and reset restore, publish removes, invalid result rejected, creation and editing still work); for complete Lab deletion (success, running, starting/stopping, unknown status, status-check failure, retry after stopping, wrong confirmation, missing pending intent, Lab outside context, pending workspace changes, published hash conflict, concurrent startup, concurrent publication, publisher failure, trash recovery, other conversations unaffected); real Claude CLI tests (delete approved files, not without approval, not usecase.yaml, no access to other workspaces, no emptying workaround, correct directive for complete deletion, running-Lab blocker handled conversationally).
> PART D — two independently testable stages: Stage 1 individual file deletion; Stage 2 complete Lab deletion. PART E — acceptance criteria (Claude deletes approved files; Review shows deleted; undo/reset restore; publication removes; usecase.yaml cannot be deleted individually; separate confirmation for a whole Lab; running Labs cannot be deleted; blockers explained conversationally; user can stop the Lab and resume; the Lab goes to recoverable trash; no permission broadened; all regression tests pass). PART F — final report. Do not restart services; do not modify or reset the existing clickhouse-operator workspace; no destructive operation on existing published Labs.

## Cause that led to it

A deletion order was carried out by emptying the 14 files of a Lab (zero-byte files, 68 validation errors): Claude had Write and Edit only, no way to delete.

## Implemented

### Stage 1: files of a Lab

- `ai-builder/labfs_mcp.py` (new): a stdlib MCP server (stdio) with one tool, `delete_file(lab, path)`. Claude Code starts it only for an editing turn, with `--mcp-config=<json>` listing exactly the working copies approved for that message (`conversation_args(..., delete_labs=...)`), and `--allowedTools` gains `mcp__labfs__delete_file`. A read-only turn has neither the server nor the grant (the one-shot approval lifecycle is the lifecycle of the tool). `--strict-mcp-config` stays, Bash stays denied, no filesystem permission is added.
- `ai-builder/workspace.py` `delete_file(work, rel)`: plain relative path (`[A-Za-z0-9_.-]` segments), not the root `usecase.yaml`, no symlink on the path or as the target, a regular file only (no directory, nothing recursive), resolved inside the working copy; empty parent directories are removed, never the working copy.
- Deleted files are an ordinary `deleted` change of the working copy: Review Changes lists them as deleted, Undo and Reset restore them (snapshots are manifests), publication replaces the whole Lab tree (`publishing.publish_tree` swaps the validated tree), so removed files disappear and nothing outside the target Lab is touched.
- `publishing.publish_tree` refuses a tree without a regular root `usecase.yaml` before anything else (the validator also rejects it, and the backend review shows it).
- Prompts: system prompt and editing notes name the tool and forbid emptying files; `PROMPT_REV` is 8 (a resumed session gets the current rules once).
- UI: after a publication that removed files, the result line warns that an already running environment is not changed.

### Stage 2: a whole Lab

- Directive `[[context: delete LAB]]` (trailing block only, like the others). `ConversationManager._propose_delete` records `delete_request` in the conversation (kept across ordinary turns and restarts, cleared by Cancel (`decline_delete`), success, or the Lab leaving the context). It never combines with an edit or creation request in the same reply. Nothing is deleted or approved.
- Infrastructure verdict: only the web server can see Docker. `web/lab_delete.py` (`DeleteGate`, stdlib) answers `stopped` only when a fresh `engine/usecase-list.sh` query lists the Lab with zero clusters; starting, stopping, deleting, unknown, a failed query or an unlisted Lab are not stopped (fail closed).
- `POST /api/ai-builder/conversations/<id>/delete_check` (web): the browser names the Lab; the server adds the verdict and forwards. Anything but `stopped` makes the AI Builder append the explanation to Claude's reply (running / starting / stopping / could-not-verify) and keep the request; the user says it is stopped, Claude emits the directive again, and the check runs again, so the user's word is never trusted. `stopped` records the published tree hash and lets the card appear.
- Card: Lab name, title, file count, permanent-removal warning, warning about other conversations; the Delete button stays disabled until the exact name is typed.
- `POST /api/ai-builder/conversations/<id>/delete_lab` (web) marks the Lab as being deleted under the same lock that registers start/stop operations (`_launch` refuses a start with 409 meanwhile; a start already registered refuses the deletion), verifies Docker again, and forwards `{lab, confirm, infrastructure}` built by the server (a verdict sent by the browser is never forwarded). The AI Builder (`ConversationManager.delete_lab`) re-verifies: conversation idle and not publishing, Lab in context, pending request, typed name, `infrastructure == "stopped"`, no unpublished changes in that Lab's working copy, no publication or deletion of that Lab in progress, published hash equal to the hash recorded at the check. Editing approval is never consulted.
- Publisher: `POST /delete {name, expected_hash}` (same token and Host gates) → `publishing.trash_tree`: valid name, real directory (no symlink), hash equal to `expected_hash`, one atomic `os.rename` to `usecases/.trash/<lab>-<UTC time>-<token>/` (never overwrites, no `rm -rf`, no purge), plus `<destination>.json` with the restore command. Publications and deletions of a publisher never overlap (one lock). `builder.usecase_names` ignores dot directories; `engine/usecase-list.sh` already skips them; `.gitignore` has `usecases/.trash/`.
- After success: request cleared, Lab detached (the next Lab of the context takes over), approvals of that Lab revoked, a confirmation is appended to the conversation, Claude is told in the next message, and the conversation's own working copy is moved aside (`<id>+<lab>`), not destroyed (removed with the conversation). Other conversations are untouched; their working copies show a conflict and cannot publish.

## Recovery

`mv usecases/.trash/<lab>-<time>-<token> usecases/<lab>` from the repository root on the host (the `.json` next to it says so). Nothing is purged automatically; delete old trash entries by hand when sure.

## Known limitations

- A Lab started from a terminal (not through the web server) cannot be excluded by a lock: the fresh Docker query right before the move is the only protection for that case, and it has a small window.
- The infrastructure check relies on the Playground's own discovery (`engine/usecase-list.sh`); it cannot see clusters of other tools.
- The trash is never purged and has no restore button.
- The container deployment (compose, real Docker discovery, the `ai-publisher` route) was not exercised here.
